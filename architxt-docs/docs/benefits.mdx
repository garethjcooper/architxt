# Query your architecture, don’t hunt for it.

Architecture knowledge lives in documents, diagrams, wikis, tickets, architecture decision records (ADRs), and the heads of experienced people. That scattering has a real cost. architxt turns those scattered, decaying design artifacts into a structured, queryable architecture layer — without replacing your enterprise-architecture (EA) framework or sending proprietary information outside your infrastructure.

---

## Bridge existing information and new knowledge stores

The direction of the field is convergent: unstructured documents, existing repositories, and new AI-powered knowledge stores will increasingly be treated as parts of one architecture-knowledge ecosystem rather than separate silos. Large language models (LLMs) and knowledge graphs are seen as complementary, not competing. However, convergence does not eliminate the need for a **bridge** — a layer that maps existing, often informal information onto stable, queryable entities that newer knowledge stores can consume, cross-reference, and reason over. architxt aims to be that bridge.

See the [full paper index](#full-paper-index) for the research sources behind this section.

---

## Complement, not replace

architxt is an IT-architecture knowledge workbench that works with the design information you already have, in the formats you already use. It extracts entities, relationships, and decisions from documents, diagrams, wikis, tickets, and ADRs, links them to stable IDs, and makes the result queryable. It does not require you to abandon TOGAF, ArchiMate, ITIL, ITAM, Ardoq, LeanIX, or any other EA framework or modelling tool; it sits beside them and fills the gap between formal governance models and the informal, scattered detail that actually drives day-to-day decisions.

In practice, that means:

- **No rip-and-replace.** Keep your existing taxonomy, repository, and service-management tooling.
- **No clean-up front.** Ingest heterogeneous, imperfect sources as they are; quality gaps are surfaced and can be addressed before ingestion, not hidden.
- **No ontology project.** The model is anchored to real-world architecture items rather than to a heavyweight schema. It uses the lightest possible ontology to retain its connection to the enterprise's other systems.
- **No external LLM required.** Can run fully on-premise with open-source models when data sovereignty matters.

## 1. Save time finding architecture information

Software practitioners spend a large fraction of their day searching for and using information. For architects, that information is scattered across many sources — docs, diagrams, wikis, tickets, ADRs — so the overhead is multiplied.

### How architxt addresses this

This is the foundational “time saved” benefit. We use the academic 32% figure in place of the commonly quoted but unverifiable McKinsey / IDC / Gartner “19–30% searching” statistic. It is not architecture-specific, but it grounds the time-loss claim in a citable source. architxt reduces that overhead by making the architecture layer queryable from one place.

### Supporting evidence

| Paper | Key finding |
|---|---|
| Al Haque et al. — [A Survey on Software Engineering Data](https://arxiv.org/abs/2408.04032) (arXiv:2408.04032, 2024) | ~**32%** of a software practitioner’s day is spent seeking and using information. |
| Jean de Dieu et al. — [Leveraging Machine Learning for Software Architecture Recovery](https://arxiv.org/abs/2112.10920) (arXiv:2112.10920, 2021) | Architects spend too much time going through many dispersed sources to recover architecture knowledge. |

## 2. Query for specifics with accuracy and quality

Stakeholders need precise answers from architecture documents — “which services depend on X?”, “what was the rationale for this decision?”, “where is this quality attribute handled?”. Large language model (LLM) + retrieval-augmented generation (RAG) + knowledge-graph approaches are shown to improve enterprise question-answering (QA) accuracy and traceability compared with plain document search.

### How architxt addresses this

This bridges the “time saved” benefit to “quality of answers.” It positions architxt as a query tool, not a static wiki. The 0.86 F1 figure is useful because it shows architecture concepts can be automatically extracted from documents at useful accuracy, and then queried with grounding.

### Supporting evidence

| Paper | Key finding |
|---|---|
| Sequeda — [The AI RDF Knowledge Graph Connection](https://arxiv.org/abs/2311.07509) (arXiv:2311.07509, 2023) | KG-based grounding improves factual accuracy of LLM answers over enterprise data. |
| Chakraborty — [Knowledge Graph RAG: Agentic Crawling and Graph Construction in Enterprise Documents](https://arxiv.org/abs/2604.14220) (arXiv:2604.14220, 2026) | KG/RAG shows precision gains for enterprise question answering. |
| Chen — [VDGR-RAG: Vectors, Directories, Graphs, and Reflection Are All You Need for Unified Reasoning over Hierarchical Enterprise Knowledge](https://arxiv.org/abs/2608.07994) (arXiv:2608.07994, 2026) | KG/RAG shows precision gains for enterprise question answering. |
| Fuchß et al. — [Who’s Who? LLM-assisted Software Traceability with Architecture Entity Recognition](https://arxiv.org/abs/2511.02434) (arXiv:2511.02434, 2025) | Architecture entity recognition achieves F1 ~**0.86** without hand-built models. |

## 3. Detect gaps, seams, and architecture erosion

Architecture drift and erosion happen silently and harm quality and evolution. Manual consistency checking is laborious and error-prone. A queryable architecture model makes it easier to spot violations, duplicates, cyclic dependencies, and missing coverage.

### How architxt addresses this

This is the “health check” benefit. architxt is not a code analyzer competing with SonarQube, ArchUnit, or CodeScene. The gap detection is at the design/model layer — missing entities, inconsistent relationships, undocumented decisions — and a queryable model makes those problems visible earlier.

### Supporting evidence

| Paper | Key finding |
|---|---|

| Li et al. — [Architecture Erosion: Symptoms, Causes, and Detection](https://arxiv.org/abs/2201.01184) (arXiv:2201.01184, 2022) | Erosion symptoms include violations, duplicate functionality, and cyclic dependencies. |
| Greifenberg et al. — [Consistency Checking of Models and Code](https://arxiv.org/abs/1510.08510) (arXiv:1510.08510, 2015) | Manual consistency checking is **laborious and error-prone**. |

## 4. Discover current-state architecture

Enterprise architecture knowledge is scattered across requirements documents, design diagrams, code comments, wikis, and other artifacts. EAM success depends on information availability. architxt builds a queryable as-is model from existing documents.

### How architxt addresses this

“Discover current state” is distinct from “find information faster.” Finding information is about point queries; discovering current state is about assembling a coherent, queryable model of the as-is architecture. This is a larger, more strategic benefit area.

### Supporting evidence

## 5. Stop design-document shelfware / preserve design value

Solution-design documents, ADRs, and architecture rationale are often created once, used for an immediate decision, and then left to rot. Outdated docs, incomplete ADRs, and loss of expert knowledge waste prior design effort. architxt keeps these artifacts alive as a reusable, queryable knowledge base.

### How architxt addresses this

“Shelfware” is not a direct academic term, so we map it to adjacent concepts: documentation debt, stale docs, incomplete ADRs, and tacit expert knowledge loss. The evidence does not provide a clean “X% of design documents are never reused” figure, but the surrounding evidence is strong. architxt keeps design rationale alive by attaching it to stable entities and making it queryable long after the original decision was made.

### Supporting evidence

| Paper | Key finding |
|---|---|
| Tan et al. — [Outdated Code-Element References in GitHub Projects](https://arxiv.org/abs/2212.01479) (arXiv:2212.01479, 2022) | Outdated code-element references are **pervasive across 3,000+ GitHub projects**. |
| Silva et al. — [Documentation Defects in Open-Source Software](https://arxiv.org/abs/2402.11048) (arXiv:2402.11048, 2024) | In 101 documentation defects, the biggest contributors are missing docs (35), erroneous examples (23), and outdated content (19). |
| Miccio Palermo et al. — [What Do Architecture Decision Records Really Capture?](https://arxiv.org/abs/2609.07375) (arXiv:2609.07375, 2026) | ADRs often **under-document alternatives, drivers, and quality concerns**. |
| Cervera — [Expert Mind: A Retrieval-Augmented Architecture for Expert Knowledge Preservation](https://arxiv.org/abs/2603.14541) (arXiv:2603.14541, 2026) | The departure of subject-matter experts causes **irreversible loss of tacit knowledge** rarely captured by conventional documentation. |

## 6. Faster architect onboarding / time to first useful output

New architects face a long ramp before they understand the existing architecture well enough to contribute. Effective onboarding is correlated with productivity and job satisfaction, yet it is often lengthy, costly, and error-prone. A structured, queryable architecture map accelerates that ramp.

### How architxt addresses this

This area is framed around documents, models, and visualisation rather than code analysis. The evidence consistently describes onboarding as lengthy and costly, and shows that structured comprehension aids improve it. A queryable architecture model is the same kind of structured ramp-up surface for new architects.

## 7. Data sovereignty, on-premise, and open-source

Architecture documents describe systems, boundaries, vendors, data flows, and sometimes regulated information. Many organisations cannot or will not send that content to a remote, proprietary LLM. architxt can be fully self-hosted on open-source models, keeping proprietary architecture knowledge under the organisation’s control.

### How architxt addresses this

This is a procurement and governance differentiator rather than a productivity benefit. It matters most for regulated industries, government, and large enterprises with strict data-residency policies. architxt is open-source and can run on local open-source models, so organisations can keep proprietary architecture knowledge inside their own infrastructure.

### Supporting evidence

| Paper | Key finding |
|---|---|
| Paloniemi et al. — [Porting an LLM based Application from ChatGPT to an On-Premise Environment](https://arxiv.org/abs/2504.07907) (arXiv:2504.07907, 2025) | Cloud LLMs conflict with **legislation related to privacy and security of data**; organisations port to on-premise environments where privacy and security can be controlled. |
| Huang et al. — [A Middle Path for On-Premises LLM Deployment](https://arxiv.org/abs/2410.11182) (arXiv:2410.11182, 2024) | **“Privacy-sensitive users require deploying large language models within their own infrastructure (on-premises) to safeguard private data and enable customization.”** |
| Huang et al. — [Securing LLMs in the Wild](https://arxiv.org/abs/2607.13088) (arXiv:2607.13088, 2026) | Cloud deployments raise concerns over **data sovereignty, compliance, latency, and third-party dependence**, driving organisations toward edge and on-premise LLMs. |
| Gupta & Shrivastava — [Zero Data Retention in LLM-based Enterprise AI Assistants](https://arxiv.org/abs/2510.11558) (arXiv:2510.11558, 2025) | For healthcare and finance, **governance of data, compliance, and business privacy** is a priority; zero data retention is an active architectural concern. |
| Yew et al. — [The Commodification of AI Sovereignty](https://arxiv.org/abs/2601.11763) (arXiv:2601.11763, 2026) | “Sovereignty” is now part of national AI policies and enterprise procurement. |
| Pan et al. — [A Cost-Benefit Analysis of On-Premise Large Language Model Deployment](https://arxiv.org/abs/2509.18101) (arXiv:2509.18101, 2025) | Organisations weigh commercial cloud services against local open-source models due to **data privacy, vendor lock-in, and long-term operating costs**. |
| Zeng et al. — [Mitigating the Privacy Issues in Retrieval-Augmented Generation (RAG)](https://arxiv.org/abs/2406.14773) (arXiv:2406.14773, 2024) | RAG over private data creates **severe privacy risks** and potential leakage of sensitive information. |
| Kooy et al. — [Impact and Implications of Generative AI for Enterprise Architects](https://arxiv.org/abs/2510.22003) (arXiv:2510.22003, 2025) | GenAI supports design ideation, artifact creation, and architectural decision support, but reported risks include **privacy and compliance concerns**. |

## Barriers to success

The benefits above are only possible if a tool can handle the messy reality of architecture knowledge. Two barrier areas keep organisations from getting good answers today.

### Barrier 1: Existing data location, format, and quality

Before a tool like architxt can query an architecture, the existing knowledge must be accessible, interpretable, and sufficiently complete. In practice it is not. Architecture knowledge is scattered across many artifact types and storage locations, captured in inconsistent formats, and kept current only sporadically. These barriers directly limit the quality of any downstream query, retrieval, or analysis.

### How architxt addresses this

architxt reduces this barrier by ingesting documents, diagrams, wikis, tickets, and ADRs in the formats they already exist in, then normalising and linking their content to stable entities. It does not require a clean-up front: extraction, entity disambiguation, and relationship inference are part of the pipeline. Gaps in the source material are surfaced in the queryable model, so teams can see where their architecture knowledge is thin rather than assuming the tool is broken. The result is a working as-is model built from the degraded but real information the organisation actually has.

### Supporting evidence

| Paper | Key finding |
|---|---|
| Zhang, Wan, Xia, Jiang & Lo — [Software Architecture in Practice: Challenges and Opportunities](https://arxiv.org/abs/2308.09978) (arXiv:2308.09978, 2023) | Qualitative study of **32 practitioners from 21 organisations across three continents**. Documentation-specific barriers include inadequate models/tools for completeness, docs becoming obsolete as software evolves, and inadequate tool support for sharing, version control, and tracing scattered design docs. |
| Keim & Kaplan — [Architecture Knowledge Management SLR](https://arxiv.org/abs/2601.19548) (arXiv:2601.19548, 2026) | Architectural knowledge is **scattered across heterogeneous software artifacts**, making it hard to access and utilise. |
| Enterprise Architecture Model Transformation Engine — [arXiv:2108.13169](https://arxiv.org/abs/2108.13169) (2021) | The **heterogeneity of modelling frameworks and description languages** makes concatenation and integration of enterprise architecture models considerably difficult. |
| Polystore Architecture Using Knowledge Graphs — [arXiv:2308.03584](https://arxiv.org/abs/2308.03584) (2023) | Modern applications manage datasets with **heterogeneous data and schemas**, making integrated access difficult. |
| Cervera — [Expert Mind](https://arxiv.org/abs/2603.14541) (arXiv:2603.14541, 2026) | The departure of subject-matter experts causes **irreversible loss of tacit knowledge** rarely captured by conventional documentation practices. |
| Greifenberg et al. — [Consistency Checking](https://arxiv.org/abs/1510.08510) (arXiv:1510.08510, 2015) | Manual consistency checking is **laborious and error-prone**. |

### Barrier 2: Domain expertise and pipeline-design effort

Even when source documents exist, building a useful queryable architecture model from them is not automatic. It requires understanding the problem domain, choosing what entities and relationships matter, designing extraction and normalisation pipelines, validating quality, and maintaining the model as sources change.

### How architxt addresses this

architxt lowers this barrier by shipping a domain-aware architecture pipeline rather than a blank knowledge-graph canvas. It extracts entities and relationships from architecture documents without hand-built models, aligns them to stable IDs, and lets the user tune the model through the UI rather than by writing ontology definitions. T-RAG confirms that robust enterprise RAG demands deep domain work; architxt does that work out of the box for IT architecture artifacts, so the team can start querying before they have designed schemas or extraction rules.

### Supporting evidence

| Paper | Key finding |
|---|---|
| T-RAG — [T-RAG: Lessons from the LLM Trenches](https://arxiv.org/abs/2402.07483) (arXiv:2402.07483, 2024) | “While building a RAG is relatively straightforward, **making it robust and a reliable application requires extensive customization and relatively deep knowledge of the application domain**.” |
| Fuchß et al. — [Who’s Who? LLM-assisted Software Traceability with Architecture Entity Recognition](https://arxiv.org/abs/2511.02434) (arXiv:2511.02434, 2025) | Extraction achieves F1 ~**0.86**, but that is only one step. Schema design, relationship inference, and quality validation remain. |
| OntoEKG — [LLM-Driven Ontology Construction for Enterprise Knowledge Graphs](https://arxiv.org/abs/2602.01276) (arXiv:2602.01276, 2026) | Construction of enterprise-knowledge-graph ontologies remains a **resource-intensive, manual process that relies heavily on domain expertise**. Fuzzy-match F1 only **0.724** in the Data domain. |
| Knowledge Graph Curation — [A Practical Framework](https://arxiv.org/abs/2208.08130) (arXiv:2208.08130, 2022) | Knowledge graphs inevitably contain errors, duplicates, and missing values. **Low-quality KGs produce low-quality applications** built on top of them, so curation is essential. |
| LLMATCH — [A Unified Schema Matching Framework with Large Language Models](https://arxiv.org/abs/2507.10897) (arXiv:2507.10897, 2025) | Schema matching is foundational for enterprise data integration, but aligning disparate data sources remains hard. |
